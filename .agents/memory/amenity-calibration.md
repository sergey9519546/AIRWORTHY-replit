---
name: Amenity revenue calibration
description: How amenity revenue-impact percentages are derived from real listing data vs. the fixed heuristic fallback, and how the cache stays fresh
---

Amenity impact percentages (pool, hot tub, parking, EV charger, gym, pet-friendly, workspace) are calibrated from `listings.amenities` free-text vs. `estimated_revenue_l365d`, comparing with/without averages **within the same bedroom-count bucket** (to control for the "bigger homes have more amenities and more revenue" confound). Calibration is computed at two grains simultaneously — per state and per (state, city) — using the same minimum-sample thresholds for both; a city (e.g. `ca`/`los-angeles`) can have a very different calibrated impact than its state average (observed: LA pool +22% vs. CA state-wide +4%), so city-level is preferred whenever it has enough support.

**Why:** A global fixed percentage (e.g. "pool = +6%") was a disclosed guess; real per-market data was already sitting in the InsideAirbnb `amenities` column and unused for this purpose. State-level alone (the first iteration) masked large intra-state variation between big cities and smaller markets.

**How to apply:** `amenity_calibration.lookup(state, amenity_key, city_slug=None)` checks the city entry first (if `city_slug` given and data-backed), then falls back to the state entry, then returns `None`. Callers (`enrichment.amenity_multiplier`/`amenity_drivers`, both now accepting a `city_slug` kwarg) fall back further to the fixed heuristic in `enrichment.AMENITIES` and disclose it as a rough (non-data-backed) estimate via `is_data_backed: false` when neither grain has enough data. `market_estimator.estimate_from_db` passes the modal comp city (`city_slug`) already computed for the response's `market.borough` field — no extra query needed. The calibration cache (`compute_calibration` returning `{"states": {...}, "cities": {(state, city): {...}}}`) is keyed by the newest `snapshot_date` in `listings` (same freshness signal `/api/cities` exposes) — a cheap `MAX(snapshot_date)` check runs on every call, and the full-table recompute only fires when that value changes, so newly loaded market data is picked up without a server restart.

**Recompute is off the request path:** the full-table scan runs on a daemon background thread (`_recompute_in_background`), guarded by a lock plus an in-flight-snapshot marker so a burst of concurrent requests after a data load only starts one recompute. `get_calibration()` always returns immediately — the last-known cache while a recompute is pending, or `{}` on the very first-ever call before anything has been computed. That means right after boot / right after a fresh snapshot, `lookup()` can return `None` and callers fall back to the fixed heuristic for a short window until the background recompute finishes; there's no proactive startup warm-up yet (tracked as a follow-up).
