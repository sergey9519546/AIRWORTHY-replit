# AIRWORTHY — COMPLETE PRODUCT-LED UI/UX REDESIGN

## ROLE

Act as a senior product designer, creative director, UX architect, data-visualization designer, and frontend engineer.

Your task is to inspect the existing AIRWORTHY project, understand how the current product works, and redesign the entire user experience into a distinctive, production-quality short-term-rental revenue estimation platform.

Do not make a superficial visual refresh.

Do not simply change colors, fonts, cards, border radii, or hero imagery.

Reconsider the product hierarchy, information architecture, interactions, visual language, page composition, data presentation, and user journey from first principles.

---

# 1. PRODUCT DEFINITION

AIRWORTHY is a tool that estimates how much a residential property could earn if operated as a short-term rental on platforms such as Airbnb, Vrbo, and Booking.com.

The core user job is:

> Enter a property and understand how much it could realistically earn as a short-term rental.

The user should be able to answer:

1. How much could this property earn annually?
2. How much could it earn each month?
3. What occupancy and nightly rate support that estimate?
4. How reliable is the estimate?
5. Which comparable properties were used?
6. What property features increase or reduce revenue?
7. How would the estimate change if the property or assumptions changed?
8. How does the property compare with the surrounding market?

AIRWORTHY is not primarily:

* A mortgage calculator
* A real-estate brokerage
* A generic investment dashboard
* A property-management platform
* An aviation-themed product
* A luxury-property marketing website
* A broad “AI property intelligence” platform

Do not expand the product into unrelated features.

---

# 2. PRIMARY PRODUCT PROMISE

The main positioning should be:

> See what any property could earn.

Supporting explanation:

> Estimate short-term-rental revenue using comparable listings, local demand, occupancy patterns, seasonality, and nightly pricing.

Primary action:

> Estimate earnings

The product must feel immediate and understandable. The user should not need to understand advanced real-estate terminology before receiving value.

---

# 3. STRATEGIC DESIGN DIRECTION

Create AIRWORTHY as a:

# Property Earnings Instrument

The experience should feel like a refined measurement system for short-term-rental earning potential.

It should combine:

* Editorial clarity
* Geospatial intelligence
* High-end data visualization
* Direct manipulation
* Calm product UX
* Strong typography
* Progressive disclosure
* Clear evidence and confidence
* Sophisticated motion used only when it improves understanding

The final product should feel closer to a high-end spatial analysis tool than a conventional SaaS dashboard.

Use the design principles found in work by studios and products such as:

* Work & Co
* Studio Freight
* Unseen Studio
* Locomotive
* Basement Studio
* Felt
* Linear
* High-end Mapbox implementations

Learn from their methods:

* Product logic generates the visual identity
* The interface should reveal information progressively
* Maps should function as interfaces, not decorative backgrounds
* Motion should explain changes and relationships
* Data should have a recognizable visual language
* Complex information should remain calm and legible
* The product should not look like a template

Do not directly copy any particular website.

# 6. SIGNATURE AIRWORTHY VISUALIZATION

Create a proprietary visualization called:

# The Earnings Envelope

AIRWORTHY should not rely on one falsely precise revenue number.

The primary result should be a modeled range:

```text
ESTIMATED ANNUAL REVENUE

$78,400 — $94,100

Most likely: $86,200
```

Represent this as a refined probability or forecast field, not a basic progress bar.

It should communicate:

* Downside case
* Likely range
* Most likely estimate
* Upside case
* Confidence
* Market benchmark

The Earnings Envelope should become a recurring brand asset across:

* Homepage estimates
* Property reports
* Map selections
* Saved properties
* Property comparisons
* Exported reports

It should look unique to AIRWORTHY and not like a generic chart-library component.

---

# 7. CORE USER JOURNEY

The main journey should be:

1. User enters an address, listing URL, or property.
2. AIRWORTHY identifies the property.
3. The product confirms property facts.
4. Comparable rentals are gathered and evaluated.
5. Market demand and seasonality are modeled.
6. Revenue, ADR, and occupancy estimates are calculated.
7. The user sees a clear annual revenue range.
8. The user can inspect the evidence.
9. The user can edit property facts and assumptions.
10. The estimate updates immediately.
11. The user can save, compare, or export the analysis.

Every screen and interaction should reinforce this journey.

Do not build a conventional marketing page with:

* Hero
* Feature cards
* Testimonials


The homepage should transform into a live estimate sequence.

The sequence can include:

1. Locate the property
2. Draw the parcel or location
3. Confirm property facts
4. Reveal nearby comparables
5. Resolve the Earnings Envelope
6. Display monthly seasonality
7. Present the complete result

# 9. PAGE 2 — MARKET MAP

The market map should be a spatial discovery and comparison tool.

The map must be the dominant interface, not a background behind a filter panel.

## Layout

* Map should occupy approximately 75–85% of the viewport
* Controls should be contextual and compact
* Avoid a large permanent left sidebar
* Use a top command rail and contextual bottom panel

## Search and filters

Include only filters that materially affect revenue:

* Location
* Property type
* Bedrooms
* Bathrooms
* Guest capacity
* Entire home/private room
* Pool
* Hot tub
* Revenue range
* Occupancy range
* Nightly rate
* Comparable quality

Advanced filters should be progressively disclosed.

## Map layers

Limit primary analytical layers to:

* Annual revenue
* Average nightly rate
* Occupancy
* Seasonality
* Comparable density

Do not expose every metric as a map layer.

## Visualization

Avoid covering the map with dozens of black price bubbles.

Develop a more sophisticated earnings surface:

* Market-level revenue intensity when zoomed out
* Neighborhood or grid-level earning patterns
* Property-level estimates when zoomed in
* Selected property shown clearly
* Nearby comparable properties revealed contextually
* Labels automatically decluttered
* Smooth transitions across zoom levels

## Property selection

When a property is selected:

* Quiet the surrounding map
* Reveal nearby comparable rentals
* Show the selected property clearly
* Open a bottom inspection panel

Example:

```text
2209 RIDGEWAY DRIVE

$78.4K–$94.1K annual revenue
$237 average nightly rate
67% expected occupancy
31 comparable rentals
High estimate confidence

[Open estimate]
```

The user should remain geographically oriented.

# 12. PERFORMANCE DRIVERS

Explain why the property receives its estimate.

Use plain language and estimated financial impact.

Example:

```text
POSITIVE CONTRIBUTORS

Pool and outdoor area                    +$8,900
Four-bedroom guest capacity              +$7,200
Strong summer weekend demand             +$5,100

LIMITING FACTORS

Distance from visitor district           −$4,600

Weak winter weekday demand               −$2,700
```

The user should understand the estimate without needing to interpret abstract analytics.

# 13. COMPARABLE RENTALS

Comparable properties are the evidence behind the estimate and should be treated as a primary part of the product.

Each comparable should display:

* Property image
* Match percentage
* Distance
* Bedrooms
* Bathrooms
* Guest capacity
* Key amenities
* Annual revenue
* Average nightly rate
* Occupancy
* Active months
* Review count where available
* Reason for inclusion
* Differences from the subject property

Allow the user to:

* Inspect each comparable
* Include or exclude a comparable
* See why AIRWORTHY selected it
* View the effect of removing it
* Sort by similarity, revenue, distance, ADR, or occupancy
* Compare the subject property directly with selected comparables

Do not make comparables a small sidebar widget.

# 15. CONFIDENCE AND TRANSPARENCY

AIRWORTHY must explain how reliable the estimate is.

Do not merely display:

> Confidence: High

Explain the reasons:

```text
HIGH CONFIDENCE

31 closely matched comparable rentals
92% property-type similarity
Recent market observations
Strong twelve-month listing coverage
Consistent occupancy records
Moderate amenity variation
```

Also disclose weaknesses:

* Limited comparable inventory
* Sparse recent data
* Unusual property type
* Extreme amenity differences
* Highly seasonal market
* Regulation uncertainty
* Incomplete property facts

Avoid unsupported claims such as “98% accurate.”

# 17. MOTION AND INTERACTION

Good uses of motion:

* Locating a property
* Revealing the parcel
* Connecting comparable rentals
* Resolving the earnings range
* Updating the estimate after assumptions change
* Transitioning between annual and monthly views
* Showing map layer changes
* Showing how comparable selection affects confidence

Avoid:

* Constant ambient movement
* Decorative floating elements
* Excessive parallax
* Long cinematic intros
* Slow animations that delay access to the estimate
* Motion that harms map usability

All transitions should feel fast, deliberate, and informative.

Respect reduced-motion preferences.

* Build reusable components

* Preserve working business logic unless improvement is required

* Keep product logic separate from presentation
* Use realistic property and revenue data in demos
* Include complete loading, empty, error, and partial-data states
* Optimize maps, charts, imagery, and animations
* Avoid unnecessary dependencies
* Keep performance high
* Ensure there are no broken buttons or dead-end routes

Use the project’s current technology stack unless there is a strong technical reason to change it.

Do not rebuild the entire application in a new framework only to achieve a visual redesign.
